# ChampionshipsCore

ChampionshipsCore 是 Summer/Winter Collab Championship 使用的赛事核心插件。它把一套 Minecraft 服务端组织成完整的团队锦标赛：从队伍、场地和赛程，到实时计分、观战、聊天展示和最终排名，都由同一套插件统一管理。赛事团队可以用它手动开一场测试局，也可以在正式比赛中驱动多轮赛程、记录成绩并生成最终排名。

插件内置 13 个比赛项目，覆盖宾果探索、建造还原、竞速跑酷、团队对抗和决赛场景。每个项目都支持独立地图、规则介绍、复制场地、积分规则和观战边界。

## 游戏介绍

### 宾果

所有队伍进入同一套主世界、下界和末地，共同完成 5×5 任务卡。任务会要求获得物品或药水、达成统计目标或完成进度；同一格可由多支队伍分别完成。玩家右键副手地图，即可在地图与菜单两种卡片样式间切换。

完成按先后顺序计分，横、竖或对角连线带来团队奖励。开局发放探索装备与物资，并提供队友传送；常驻效果、PvP 时机、时长和分值由 Bingo 配置决定。`LOCAL` 与 `REMOTE` 共用同一套任务判定、世界规则、玩家状态、计时格式、队伍颜色和展示策略；远程 Worker 执行 Core 冻结后的比赛 manifest，保证两端呈现一致的玩法。

### 匹配赛建

各队从公共资源大厅收集方块，在自己的建造位复刻参考建筑。普通建造位随机分配蓝图，完成后自动补充；黄金蓝图每 3 分钟轮换一次。

参赛玩家免疫摔落伤害和鞘翅撞墙伤害。

初始工具包含效率 III、不可破坏的剪刀，死亡后也会随装备恢复。资源大厅的跳板区参考 AceRace 橙色羊毛跳板：踩上后延迟一 tick，确认仍站在同一跳板上，再一次性向上弹射并沿水平朝向轻微前推。前推速度为 0.3，竖直初速度按原版重力和空气阻力计算，目标约 Y=180；视角俯仰不改变弹射高度，每次接触只触发一次，离开后再次踩上可重触发。滑翔、飞行、骑乘和旁观玩家不受影响。选区配置和编辑器统一使用 `jump-pads`（跳板区）。

开局不发放烟花火箭；正式开赛后每 10 秒为在线参赛玩家补充 1 个飞行时间为 3 的烟花火箭，背包满时掉落在玩家脚下。

提交时逐方块核对蓝图，完全一致的建筑按星级和当前计分阶段结算，未完成建筑按完成比例结算。比赛结束后，总星数、完成建筑数和平均星级还会决定排名奖励。

### 斗战方框

两队争夺中央 3×3 区域。场地可配置装备套组和瞬间伤害药水点；先用本队方块填满全部 9 格的队伍立即获胜。倒计时结束时仍未填满，则比较双方占据格数。击杀和回合结果都会计入积分。

### 跑酷追击

每场对局由两支队伍参加，并在左右两个镜像区域同时进行：每队选择一名追逐者，追捕对方的逃生者。追逐者碰触逃生者即完成抓捕；逃生者按存活时长得分，追逐者按抓捕和剩余时间得分，存活总时长较长的一方赢得对局奖励。

逃生者可用场地道具短暂干扰追逐者，追逐者也有专属的机动道具。追逐者选择次数、道具和回合时长由场地配置决定。

### 跑路战士

玩家依次挑战主检查点、子检查点和终点路线。系统记录每名玩家的重生点与检查点进度，按完成路线的星级计分；连续完成高星级路线时，单次收益递增。完成最终路线会为全队施加倍率奖励，路线、检查点、时长和倍率均由场地配置决定。

### 空岛乱斗

各队从玻璃笼和队伍出生岛进入空岛生存战。比赛按场地规则依次开放乐魂、收缩安全区域并调整生命恢复；击杀、存活和淘汰其他队伍都会计分。玩家死亡后，携带物品保存在死亡位置的箱子中。

### 去到另一边

玩家穿越障碍并击打终点鸡完成地图。地图可分别配置船、道路工具、空手或鞘翅模式，以及流浪者生成点和随机出生区域。个人越早到达得分越高，团队完成触发额外奖励；正式调度依次使用已加载场地，每张地图进行一轮。

### TNT飞跃

玩家在多层方块场地生存，脚下方块会延迟消失，指定阶段还会落下 TNT 雨。玩家可用鞘翅挽救坠落；每次淘汰奖励仍存活的玩家，轮末按生存名次结算。正式调度使用预先生成的赛道副本，并按赛程配置进行多轮比赛。

### 雪球大战

玩家以队伍颜色装备进入竞技场，使用雪球和铁剑混战。被淘汰后会在随机点复活；击杀会补充雪球，并计入个人与队伍分数。达到场地设定的击杀目标可提前结束，轮末按队伍击杀数排名结算。

### 烫手鳕鱼

每轮随机选出一名鳕鱼持有者；持有者持续受伤，攻击其他玩家可转移鳕鱼，转移后进入短暂保护期。淘汰奖励仍存活的玩家，最终按生存名次结算。正式调度将各队成员分散到多个场地，并按赛程配置进行多轮比赛。

### 龙蛋狂欢

这是两队同时进行的一场完整末影龙战。双方从镜像平台出发，使用固定装备、队伍方块和生存物资推进。队伍率先完成【解放末地】【下一世代】【远程折跃】中的任意两项即可获胜；摧毁末影水晶为全队补充物资并提供随机强化，持续伤害末影龙会给对手施加短暂负面效果。

### 躲避箭

总积分前两名进行五局三胜决赛。箭命中玩家即淘汰，淘汰对方全队即赢下一局；第一局由高顺位队伍获得两箭，后续小局双方各获得一箭。

- 玩家保持在中央分界两侧；箭在每次射击结束后消失并刷新到对方半场。
- 淘汰与累计射箭推动平台逐层收缩；管理员使用 `/cc finale dodgebolt` 下的裁判命令处理暂停、重开、淘汰和强制胜利。
- 躲避箭是决赛项目，使用专属赛程管理。

### 王牌竞速

所有选手在限时内按顺序通过进度点并完成配置圈数。正向穿过终点线结算一圈；跌落到赛段高度以下时返回最近的重生点。每个进度点可切换鞘翅、激流三叉戟或无装备，并分别配置赛段跌落高度。场地可使用速度、跳跃和定向弹射机关；完赛名次和分段名次均会计分。

### 激流勇进

停顿类躲避关已改为固定9秒的随机单只冲刺，前1秒准备。五段航程分别增加生物速度，按怪物类型设置刷新间隔和在场上限，满员跳过，出场自动回收；蜘蛛单只从随机边缘进入，苦力怕随机落在整个甲板范围。正式比赛与试玩共用实现。[移动躲避模拟、校准数据与回放](tools/riptide-dodge-sim/README.md)记录了默认7×9木筏的调参依据。

地图配置 v28 / 生成器 v28 支持移动节奏机关及观察题。解题使用 `MATH` 类型和 `math.*` 数字范围键；观察题上行显示线索，下行显示问题和左右答案，算术题上行显示算式。正式、试玩、连续门和末段侧向解题共用两行展示。当前赛道及新地图默认15穿越/5解题/5停顿（3踩色、2侧向）/5节奏，共30关。

所有参赛者出生于木筏中央同一点；传送前隐藏其他参赛者、禁用实体碰撞并清零速度及下落距离，防止重叠出生时弹开。退出、结束和重置恢复玩家原碰撞状态。

正式比赛和试玩开始时，所有关卡先呈现完整去皮云杉木墙（`STRIPPED_SPRUCE_WOOD`），统一采用施工范围的宽高和1格厚度（当前地图15宽×12高×1厚），原建筑整体隐藏；木筏前沿距离建筑前缘10格时一次性恢复原貌及洞口，连续关卡逐面显现。侧墙关卡在航道上原本没有建筑的位置同样显示占位木墙，靠近至10格时撤去；移动侧墙自身保持原貌，不遮挡。显现后不再遮挡；取消、退出试玩及结算恢复未显现的建筑，施工编辑和保存快照保留原貌。地图无需重新发布。

节奏关现在提供 26 种变体，除基础闸门和四种青色窗口外，还包括三拍脉冲、左-右-中接力、边缘换气、弹珠回弹、蛇形追拍、中心/边缘脉冲、折叠开口、分流合流、反拍留白、镜像追逐、斜线节拍、双窗交替、后拍回收和急转弯拍。新增类型按四拍切换，最短开放 0.8 秒。所有节奏门统一采用铁块墙体、红绿顶灯和音符提示；每种变体都能在编辑器选择、调权重和单关试玩。

基础七种节奏门和新增十五种组合门均固定在航道上动态开合，木筏全程继续前进，沿用穿越的离筏与掉落判定，不单独计时淘汰。显现后、船头抵达前最多约2秒启动闸门；周期按速度缩短，最短3.2秒，最短开放窗口0.8秒，红绿顶灯和音符声提示切换。关闭时完整生成墙体，并按玩家所在的一侧将重叠身体移出墙面；船尾通过或取消时恢复原方块。节奏不增加停船耗时，可配置变体、权重、次数和单关试玩，不提供建筑施工。

掉落统一由每 tick 的赛道任务采样，移动事件仅记录解题轨迹。身体与甲板边缘仍有交叠时可安全站立；短暂离开支撑保留默认0.65格水平余量，脚底下降超过甲板0.5格或无支撑越过水平边界、入水/入岩浆后，须连续保持出界20 tick（1秒）才确认掉落，回到安全位置即清零。正式与试玩共用判定，护盾救回及比赛清理会重置确认状态；断线和死亡仍按独立事件处理。

踩色全部小轮、侧向扫墙整组及末段侧向解题整组结束后，先恢复甲板/移除侧墙，再在ActionBar提示“木筏即将前进！”，保持原地40 tick（2秒）后恢复航行。等待期间仍检查玩家状态，正常扣减比赛剩余时间，并挂起下一道解题门的预览计时；正式、试玩与五分钟编排耗时估算共用等待规则。

玩家站在自动前进的木筏上，沿单轴生成赛道挑战穿越、解题、停顿、节奏四类关卡；停顿下设踩色和侧向两个子类。正式比赛固定三轮，每轮重新生成赛道并独立结算；启动时固定地图安排，按 `formal-events.RiptideRush.maps` 循环选取三次，空列表则使用已注册地图。当前 `raft` 可连续进行三轮。每轮倒计时结束时确认在线参赛者，未出场成员不计分、重连只旁观，下一轮重新取得参赛资格；正式单轮少于两名在线选手则终止赛程且本轮不计分，单人练习不受影响。

出局后可自由旁观。同一次服务器检测周期内的淘汰合并为一批，完成全部检测后判断比赛结束；同批出局互不获得生存分，其他仍存活者每超过一名实际参赛者获得4分。存活者并列第一；无人存活时最后一批出局者并列第一。第一/二/三名分别奖励100/70/30分，同批同分并按人数跳位（两人并列第一各100分，下一名第三30分）。每轮积分、护盾、淘汰名单在重置时清空；结算有重复调用保护。赛道准备失败会关闭赛程，释放参赛者及轮间保留状态。

正式积分在Core冻结玩家身份和队伍后整批写入暂存文件，不依赖结算时再次查询玩家数据库记录；数据库失败使用原事务ID自动重试，避免重复加分。暂存文件写入失败会记录错误并保留内存事务重试，此时应恢复磁盘写入后再重启。该流程同样服务远程Bingo结算，Worker协议无需变更。

穿越包含来自 HITW 的 354 个十二格木墙（13张地图的全部难度组，含156个 Very Easy–Easy 来源变体），按 bench 的去皮云杉木、楼梯、半砖、栅栏与竖起活版门转译，保留原图细部并仅局部适配普通跳跃。20% 航程后可出现双墙，40% 后可出现三墙；第二次加速（40%）后最多出现两个侧墙段；墙组要求换位或改变动作，间距随实际船速计算。侧墙段木筏停稳，每面从同一已启用穿越池抽取建筑，来向独立随机，允许连续同侧；40%–60% 每组两面，第三次加速（60%）后每组三面。真实方块从甲板半宽外7格（厚建筑额外外移）按当前船速逐格推进，每面预告1.5秒，洞口遵循原建筑；不检测触墙淘汰，沿用穿越的离筏与掉落判定。可在预览列表试玩整组或侧墙；所有玩法由正式比赛和试玩共用。穿越难度按有效门洞总截面积分为1–3级；正向门首次加速前仅1、首次后仅2、第二次后2或3，侧向门第二次加速后仅1或2、第三次后仅2或3。穿越与侧向建筑均可左右镜像，镜像固定在编排中；施工编辑保留原样。悬空一格门槛上方的1.5格半砖洞按剩余通路封实或扩大；贴地潜行洞保留。目录升级保留 bench、用户修改和删除，详见 [墙体目录与重建说明](tools/riptide-hitw/README.md)。

踩色沿用地图中的 `PAUSE` 类型，每关七轮、原地停船。五个20%航程段每轮秒数依次为：6/5/5/4/4/4/4；5/4/4/4/4/3.5/3.5；4/3.5/3.5/3.5/3.5/3/3；3/3/3/3/3/2.5/2.5；3/2.5/2.5/2/2/2/2，总时长分别32/28/24/20/16秒。方块种类依次5/6/7/8/8种。正式比赛、试玩与耗时估算共用固定节奏。七种主题均按阶段数量生成；自定义甲板保留区域布局并按阶段归并或补足材料，保存的建筑不被修改。Title显示倒计时，ActionBar仅显示目标方块；每轮目标不连续重复；进入踩色关先显示“踩在对应方块上！”1.5秒，再开始倒计时。

木筏在20%、40%、60%、80%航程加速，默认速度为2.2/2.95/3.7/4.45/5.2格每秒，最终阶段给存活玩家速度I。穿越、解题与节奏从第一次加速（20%）开始允许双连续，第二次加速（40%）开始允许三连续，仍须满足换位时间与建筑衔接。算术题初始只有加法，观察题各阶段均可出现，第一次加速后加入减法，第一次加速后开放双连续，第二次加速后开放三连续，第三次加速后加入乘法；连续解题门按各自位置决定运算范围；编排在同一加速阶段内为连续解题和节奏留足间距，无法容纳时保留较短组，第四次加速后节奏为三连门。

第四次加速（80%）后，每个正向穿越关固定生成三扇门，后两扇从启用池选择本局未使用的墙体并独立镜像；池不足时重新编排，不复用建筑补足。按所有可用出口到下一洞口的换位和动作时间留出间距，在有限末段空间内优先选择可及时到达的建筑。所有解题关和侧向关改为三面侧向解题。木筏原地停稳，甲板左红右淡蓝色混凝土，中间一列归红；每面侧墙独立出一道第五段难度的算术或观察题，并预告1.5秒。在该面侧墙完全扫过的最后一tick，按玩家脚下方块列判定答案颜色，跳跃有效，甲板外或甲板下方无效；答错出局，三题全部答对后恢复原甲板并继续航行。末段重新编排并检查建筑衔接、墙体全局唯一和五分钟总时长，无法容纳时重新抽取，不退回单门。关卡配额仍按逻辑关计数，三连包含三扇实际门；正式和整组试玩共用同一控制器。

侧墙使用原版移动活塞与史莱姆推动机制：运行时完整方块转为史莱姆，半砖、楼梯保留形状，保存的建筑快照不变。每格移动由原版活塞方块实体和客户端活塞动画完成，不再自行计算玩家推挤或传送玩家；大墙逐块驱动，不受单个红石活塞12格的结构限制。预告及换墙生成不推动，无直接触墙淘汰；结束或取消清除活塞实体并恢复原方块。

观察题包含数颜色、左右找第几项、找最大最小、数奇偶、找唯一项。五段线索数量依次4/5/6/7/8，唯一项为5/5/7/7/9，颜色种类3/3/4/4/5；第三段起使用相似两位数，第二段起索引方向随机左右。索引、极值和唯一项的两个答案都来自题面；计数干扰项为相邻的有效数量。正式、试玩及连续门使用各自位置难度，末段侧向解题使用第五段难度。

每位玩家开局有一次护盾，40%航程前抵挡出局；掉出木筏才传送回筏，解题或踩色错误原地保留。踩色首次错误消耗护盾后，本关剩余小轮的踩色错误均免淘汰，下一关清除保护；掉落与断线仍独立判定。护盾消耗或40%时到期均播放装备破碎声，并在ActionBar提示“护盾已破碎”。正式比赛、试玩与耗时估算共用阶段规则。

默认解题池包含加法、减法、乘法、连续两道解题门、观察数颜色、观察找第几项、观察找最大最小、观察数奇偶、观察找唯一项九份等权变体；单门分别使用加法、非负减法、两位数（10–99）与一位数（2–9，排除平凡的 0/1）乘法，乘数顺序随机；加减法沿用 `math.minimum-operand`/`maximum-operand`。干扰答案模拟进借位或中间数字相邻错位，优先保持位数、首位、末位一致并限制与真值的差距（最多 5% 或 10）；小于 10 的结果采用相邻干扰项。连续两道版计一个解题关卡配额，两门相距12格，各自按加速阶段随机选择已开放运算或观察题并独立判定；过第一门后显示第二题，单关试玩包含整组。连续解题和节奏按逻辑关卡计配额，40%后可扩为三门，实际间距按船速、建筑厚度与换位时间计算；编排检查整组及相邻建筑衔接，编辑建筑修改单门结构，运行时重复生成。普通侧向扫墙期间挂起前方解题门预览，恢复航行后重新给足四秒预览窗口，正式比赛和试玩一致。解题关卡按左右答案门判定，离开移动木筏、坠落或落后会被淘汰；淘汰顺序和最终存活名次计入正式赛积分。

管理员通过 `/cc map edit RiptideRush` 选择并确认地图世界，起点(.5,80,-110.5)、终点(.5,80,389.5)及330秒限时自动设定，准备页不再提供三项手动设置；加载与重新绑定世界都会修正高度。随后分别进入“穿越关卡 / 解题关卡 / 停顿关卡 / 节奏关卡”。停顿页下设“踩色 / 侧向”：停顿页设置踩色与侧向的总数量，踩色子页编辑材料变体与阶段难度；侧向查看编排规则、编辑共用穿越建筑池或进入赛道预览试玩。侧向池的建筑、启停和权重也用于正向穿越，侧向计入停顿总配额，数量为 min(2, 停顿数/2)，关闭侧向时全部为踩色。默认穿越为门洞、单栏跳跃、左右折返，解题为加法、减法、乘法、连续两道解题门、观察数颜色、观察找第几项、观察找最大最小、观察数奇偶、观察找唯一项，踩色为铜、木板、陶瓦、石材、矿石、原木、下界方块。类别页设置每局数量，解题另有数字范围，踩色展示阶段时长与方块种类。

侧向来墙提示使用 Title；末段侧向解题保留主标题题目，副标题合并来墙提醒、答案和判题倒计时。每面持续刷新，结束或取消时清理；正式比赛与试玩共用。消息配置使用 `riptiderush.sweep-title`。`PAUSE` 统一表示停顿类别，踩色和侧向共用配额。

例如修改单栏跳跃：**穿越关卡 → 单栏跳跃 → 编辑建筑**。进入施工区后直接拆放方块，也可使用 WorldEdit；默认施工范围扩大为长15格、宽15格、高12格；橙色端线和蓝色边框位于保存范围外，四角玻璃柱顶表示限高。长度固定15格，宽度随木筏宽度与 `generation.obstacle-margin` 变化，高度使用 `generation.clear-height`，菜单显示当前实际尺寸。木筏和踩色甲板仍为7×9格。使用准备工具打开施工菜单，选择“保存建筑”或确认放弃。保存包含方块朝向和方块实体数据，并直接写入该变体；复制会复制整份建筑，副本之后可独立修改。新增页可复制当前类别的任意变体（包括自建变体及副本），命名为“原名称副本”，也可直接从空白施工；空白变体保存前停用，成功保存后启用。所有变体平级，保存后的穿越建筑不再归属于门洞、跳栏或折返。建筑修改后应单关试玩，并重新发布地图。

解题保留中柱、左红右蓝边柱及两侧三格净空，以保持建筑与过门判题一致；其余框架、材质和装饰可编辑。踩色可以实际修改甲板的每格方块，保存后按阶段调整材料种类、七轮沿用区域布局并随机选择不同目标；甲板须铺满至少两种支持的陶瓦、木板、石材、涂蜡铜块、矿石、原木或下界方块，目标须分散，甲板上方三格留空。穿越保存不再校验连续可通过通道、最低通行高度或跳跃高差，保留施工范围与非空建筑检查；可玩性由管理员实际试玩确认。解题门也不检查贯穿整座建筑的路径，仅保留判题结构要求。

施工中其他准备工具统一打开保存/放弃菜单，不能生成预览或发布覆盖当前施工。确认放弃、退出编辑、断线或卸载不把未保存建筑写入变体；下次生成会清除施工预览。输入、选择、删除、分页与试玩返回保留来源页面。允许清空关卡池并保存草稿，发布仍须通过编排校验。
编排使用 `course.counts.pass/math/pause/rhythm` 配额，默认15/5/5/5，总数最多64。首尾为穿越，允许不同特殊类型相邻，最多连续两关；停顿按数量划分航线区段，每段安排一关，第二次加速后其中最多两关为侧向，其余为踩色。每份穿越墙体全局最多使用一次，正向墙、侧墙及末段新增墙共用额度，复制相同建筑快照也不增加额度；穿越不再提供抽取次数设置。连续正向墙及相邻侧墙必须没有重合的横向通行位置，仅改变门槛高度或潜行动作不算换位，侧墙检查同时考虑来向与镜像。缺少已知洞口元数据的自建建筑仅允许单独出现，不加入连续墙，不恢复施工路径搜索。穿越难度沿用上述20%/40%/60%分段；内置折返建筑不用于开局或超过2.8格/秒的位置；自定义建筑同时按其难度与实际占用长度检查衔接。长建筑无法满足间距时，需减少关数或缩短建筑。符合约束的条目按权重抽取，其他类型保留重复权重衰减与单局上限。生成前检查池容量、航线间距、按船速计算的衔接时间和整条赛道逐tick耗时；不满足时给出错误，不能发布或开赛，仍可保存草稿。

“赛道设置与预览”显示自动航线与限时，管理64位整数预览种子和正式对局随机/固定种子。进入预览后可换一条赛道、分页查看顺序和预计耗时、生成整条建筑或整条试玩；点击某关进入详情，再选择“生成并前往此关”或“试玩这一关”。变体属性页也可直接试玩新变体；试玩结束或主动退出后返回发起页。试玩3秒后开始，复用正式对局的甲板移动、解题过门与踩色判定，不记录成绩；交换副手键（默认F）退出，潜行可正常用于过门。退出/断线/卸载恢复编辑物品栏和甲板。试玩或生成期间禁止继续修改与保存地图。

`course.preview-seed` 只控制预览；`course.fixed-seed` 为空时正式对局每局随机，菜单可锁定当前种子并恢复随机。相同地图配置、关卡池及生成器版本下，种子复现顺序、建筑变体、题目和踩色内容；日志保存种子、生成器版本、解题范围及各关位置、变体、内容种子和建筑标识摘要。每场只生成一份不可变方案，物理建筑、题目、过门判定和踩色触发共同读取它。发布保存配置和一条预览赛道；正式准备前在恢复的地图上分批清理和重建自有障碍区域，再进入倒计时，区域外景观保持不变。

地图编辑侧栏定时刷新只检查基础配置、建筑尺寸和关卡池容量，不执行整条赛道搜索；侧栏的配置进度与缺项数不代替主动校验。点击“校验”、预览、发布和正式准备时仍执行完整编排检查。关卡池解析结果与固定建筑的正向/镜像通道数据复用不可变快照，编辑、重载和保存失败回滚后读取最新内容。

RiptideRush 当前只读取 v28 配置格式和 `course.pool` 关卡池，不再自动迁移历史配置或旧生成器字段；格式变更直接更新默认资源和实际运行配置。自定义建筑以 Sponge V3 方块快照保存在地图配置中，复制/删除不依赖共享外部文件。种子重现要求相同生成器版本与相同建筑配置。建筑或规则修改后应重新校验并发布地图。手动启动命令为 `/cc game start riptide all <场地>`，Core 专属玩法不涉及 Bingo Worker。

## 运行要求

- Java 25
- Paper 26.2.x 对应的服务端
- MariaDB 或 MySQL
- ProtocolLib 5.4.0
- PlaceholderAPI 2.12.2
- FastAsyncWorldEdit 2.15.0

ProtocolLib、PlaceholderAPI 或 FastAsyncWorldEdit 缺失时，ChampionshipsCore 会在启动阶段自行禁用。

## 构建与安装

```bash
mvn clean package
```

构建完成后，将 `target/ChampionshipsCore-1.3-SNAPSHOT.jar` 与三个必需依赖放入 Paper 服务端的 `plugins/` 目录，然后启动一次服务端生成配置。

仓库同时包含共享协议、Bingo 计分引擎、Paper/Folia 平台层、Redis transport、独立 Bingo Worker、压测插件、Core 插件和可选认证组件。根目录构建会生成 Core 与 Worker 两个主要制品。共享契约分布在 `championships-common`、`championships-bingo-engine`、`championships-platform-bukkit` 和 `championships-redis`；这些模块或跨端玩家可见行为发生变化时，Core 与 Worker 需成对构建、部署和重启。

`championships-auth-bridge` 部署在 Paper 侧，负责账号绑定资料同步和登录 UUID 核对；`championships-auth-proxy` 部署在 BungeeCord 侧，在登录阶段执行账户准入、封禁检查和有效 UUID 注入。Proxy 持久化身份同步快照；同步源短暂不可达时，已同步玩家仍可进入服务器并由本地 AuthMe 验证密码。UUID 的跨组件边界见 [player-uuid-contract.md](docs/player-uuid-contract.md)。

远程 Bingo 可通过 `bingo.execution-mode: REMOTE` 把世界与玩法执行交给独立 Folia Worker；`LOCAL` 模式保留单服执行方案。部署前阅读 [Worker README](championships-bingo-worker/README.md)、[跨服架构与上线流程](docs/bingo-remote-architecture.md) 和 [64 人性能指南](docs/bingo-64-player-performance-report.md)。性能指南中的逻辑玩家压测覆盖区块与实体负载；真实客户端的端到端验收是生产上线的最后一层确认。压测插件只临时安装在可丢弃的测试世界。

Bingo 任务机制与图集来自上游 [MineBingo](https://gitee.com/chancelethay/minebingo)，并按 ChampionshipsCore 的服务端版本、资源获取条件与计分体系持续适配；默认卡片与难度表由资源契约测试保护。其三页任务投票接入 ChampionshipsCore 的 DAILY 自由游玩，共用 `daily-vote.seconds` 的单一倒计时和 CC 原有大厅、Party、匹配与临时队伍。正式赛与管理员手动局继续使用场地原有固定积分规则。投票期间再次打开 DAILY 大厅或点击匹配菜单中的 Bingo 会返回当前投票页，仅本次投票参与者可进入。Core 本地局与 Worker 均在正式开局准备时使用共享安全散点服务分布参赛者，重连优先恢复离线位置。Bingo 准备倒计时固定横向位置并禁止起跳，但允许重力下落着地；共享散点服务记录实际参数、成功落点及回退/传送失败，便于核对实机分布。

推荐的首次部署顺序：

1. 创建 MariaDB/MySQL 数据库和专用账号。
2. 首次启动服务端，让插件生成 `plugins/ChampionshipsCore/`。
3. 修改 `config.yml` 中的数据库连接、队伍人数、出生点等选项。
4. 重启服务端，确认控制台没有数据库或依赖加载错误。
5. 创建队伍并添加队员。
6. 创建并配置游戏场地。
7. 先用手动命令进行测试赛，再启用正式调度器。

数据库表会在连接成功后由插件自动创建。

## 基础配置

主要配置位于 `plugins/ChampionshipsCore/config.yml`：

| 配置项 | 说明 |
| --- | --- |
| `mode` | 插件运行模式，默认 `CHAMPIONSHIP` |
| `max-players` | 赛事允许的最大玩家数 |
| `whitelist` | 满员时优先放行的玩家名列表；仅影响 Core 的人数上限，账户准入、封禁和 UUID 分配由身份桥接组件管理 |
| `weighted-score.enabled` | 是否启用游戏归一化权重和比赛轮次系数 |
| `weighted-score.round-multipliers` | 按正式比赛轮次从第 1 轮开始配置系数；超出列表的轮次按 0 计算 |
| `strict-spectator-rule` | 正式赛事模式下是否阻止参赛队员自由观战；DAILY 模式不执行此限制 |
| `enabled-games` | 本次赛事启用的游戏；未启用的游戏不会加载，也不会出现在相关命令中 |
| `database.type` | `MARIADB` 使用 MariaDB 驱动，其他值使用 MySQL 驱动 |
| `database.address` / `port` | 数据库地址和端口 |
| `database.name` | 数据库名称 |
| `database.username` / `password` | 数据库凭据 |
| `team.max-members` | 每支队伍最多成员数，默认 4 |
| `lobby.location` | 大厅出生点，也是比赛结束和地图保存时的返回点 |
| `parkourtag.max-chaser-times` | 单名队员最多担任追逐者的次数 |
| `redis.enabled` | 启用数据库缓存同步、跨服公共聊天和 REMOTE Bingo 所需的统一 Redis 生命周期 |
| `redis.instance-id` | Core 实例的稳定唯一标识；`auto` 会在数据目录持久化生成，克隆实例后必须显式区分 |
| `redis.uri` / `namespace` | Redis 连接地址和逻辑命名空间；Core 与 Worker 必须一致 |
| `redis.consumer-group-prefix` | Core 数据同步及聊天 consumer group 的前缀 |
| `bingo.execution-mode` | `LOCAL` 在 Core 内执行；`REMOTE` 把玩法执行交给 Folia Worker |
| `bingo.worker-id` / `worker-server` | REMOTE 模式的 Worker 标识与代理服务名 |

修改配置后执行：

```text
/cc admin reload
```

`enabled-games` 使用文首“配置名称”一列中的名称，不区分大小写；设为 `[]` 会关闭所有游戏。

场地配置和游戏专属配置分别位于对应游戏目录。宾果还使用 `bingo/config.yml`、`cards/`、`tags/`、`tierlists/` 和语言文件；匹配赛建使用 `buildmart/blueprints/` 中的蓝图。

Bingo 的场地文件还可通过 `permanent-effects` 调整常驻效果，格式为 `效果:等级`，例如 `night_vision:1`、`jump_boost:8`。

空岛乱斗场地通过 `variant` 选择规则方案。保留默认值 `inline` 时，计时、边界、计分和介绍文本均读取场地 YAML；填写其他名称时，插件会读取 `skywars/variants/<名称>.yml`。首次启动会生成可复制修改的 `default.yml`。

## 权限

插件只在 `/cc` 后的第一级命令上检查权限。管理员权限会自动继承玩家命令。

| 权限 | 可用功能 |
| --- | --- |
| `cc.player` | `/cc spawn`、`vote`、`spectate`、`rank` 等玩家功能 |
| `cc.admin` | 队伍、单局、正式赛事、地图、世界和裁判管理；同时可用玩家功能 |
| `cc.refuge` | 严格观战规则开启时，允许参赛队员以裁判/替补身份观战 |

建议使用权限插件分组：普通选手授予 `cc.player`，赛事管理员授予 `cc.admin`；裁判或替补按需增加 `cc.refuge`。

## 命令约定

- `<参数>` 表示必填参数，`[参数]` 表示可选参数。
- `<队伍>` 使用创建队伍时的内部名称。
- 场地设置、WorldEdit 选区和当前位置相关命令必须由游戏内玩家执行。
- 多数名称匹配区分大小写，推荐队伍名、场地名和蓝图名统一使用小写英文、数字和下划线。
- 输入到中间命令节点时，插件会显示当前节点下的帮助列表，例如 `/cc game start` 或 `/cc event`。

## 队伍与成员管理

游戏内拥有 `cc.admin` 权限的管理员可直接输入 `/cc team` 打开原生队伍管理界面。界面支持队伍总览、创建与删除、成员在线状态、在线或历史离线成员添加、成员移除，以及将单支/全部队伍传送到管理员当前位置；总览的“快速调队”可先选在线玩家再选目标队伍，已有队伍时经二次确认并以数据库事务原子迁移。原有子指令仍完整保留，供控制台和自动化使用。

### 创建队伍

命令格式：

```text
/cc team add <内部队伍名> <颜色名> <聊天颜色代码>
```

例如：

```text
/cc team add red_rabbits red &c
/cc team add aqua_axolotls light_blue &b
```

第二个参数必须是以下 Minecraft 颜色之一：

```text
white orange magenta light_blue yellow lime pink gray
light_gray cyan purple blue brown green red black
```

第三个参数用于生成队伍彩色名称和消息，可以使用 `&` 颜色代码。队伍内部名称和颜色名都应保持唯一，否则可能与主计分板队伍冲突。

数据库数字 ID 会自动生成，不需要手工输入。

### 添加队员

```text
/cc team member add <队伍名> <玩家名>
/cc team member delete <队伍名> <玩家名>
```

示例：

```text
/cc team member add red_rabbits Steve
/cc team member add red_rabbits Alex
```

每名玩家只能属于一支队伍，人数受 `team.max-members` 限制。在线成员直接使用 Bukkit/代理提供的 UUID；离线成员的 UUID 由 `identity.mode` 决定：`OFFLINE` 按 Minecraft 的 `OfflinePlayer:<玩家名>` 规则计算，`PROFILE_UUID` 调用 `identity.profile-api-base-url` 的标准档案接口，并要求返回值与登录链路一致。档案缺失、服务异常、响应格式错误或本地身份冲突会终止该次操作并提示管理员。完整边界见 [player-uuid-contract.md](docs/player-uuid-contract.md)。

### 查询、传送和删除

| 命令 | 说明 |
| --- | --- |
| `/cc team info <队伍名>` | 查看队伍成员 |
| `/cc team tphere <队伍名>` | 将指定队伍传送到命令执行者的位置 |
| `/cc team tphere all` | 将全部队伍传送到命令执行者的位置 |
| `/cc team delete <队伍名>` | 删除队伍及成员关系 |

正在参加游戏的队伍不能删除。正式建队后建议依次执行 `team info`，并让所有成员上线确认队伍颜色、聊天频道和计分板状态。

## 地图编辑与发布

地图编辑统一从游戏内向导进入：

```text
/cc map edit <游戏>
/cc map rename <游戏> <旧场地名> <新场地名>
```

`map edit` 会打开该游戏的地图列表。“新建地图”只建立尚未绑定世界的草稿，不会创建世界。之后可用 `/cc admin world create` 创建或加载世界，站在目标世界中通过向导的“绑定当前世界”步骤进行绑定；重复执行该步骤可更换绑定。已有地图可左键编辑，右键两次删除地图配置；删除地图仅移除配置关联，物理世界删除由 `/cc admin world delete` 独立处理。

`map rename` 只接受空闲且未被 prepare 锁定的地图。它会卸载对应运行实例，同时修改配置文件名、配置内 `name` 和运行时登记名，并迁移正式积分及日常赛数据库记录，然后用新名称重新加载；任一步失败都会回滚数据库、配置文件和原登记。

进入编辑会话后，插件会暂存玩家物品栏，并通过热键栏和步骤菜单引导完成世界确认、schematic、复制布局、出生点、范围、检查点、物品列表等游戏专属配置。需要范围的步骤使用 WorldEdit 选区；列表步骤在 GUI 中新增、编辑、排序或删除。完成后先执行校验，再发布地图。

发布会保存当前物理世界。未发布、存在未保存修改或正被其他管理员锁定的地图不能开赛。同一张地图同一时间只允许一名管理员编辑；正常退出会恢复原物品栏，意外掉线后的快照会在下次加入时恢复。

推荐流程：

1. 执行 `/cc map edit <游戏>`，选择已有地图或新建未绑定世界的地图草稿。
2. 使用 `/cc admin world create <世界>` 准备并加载世界，传送过去后用“绑定当前世界”步骤绑定或更换地图世界。
3. 按步骤菜单完成所有必需点位、范围、列表和复制布局。
4. 使用“校验”检查缺项，再使用“发布”保存地图。
5. 退出编辑模式，使用 `/cc game start ...` 进行单局测试。
6. 检查观战边界、比赛结束、地图重置、大厅返回和积分写入。

斗战方框、激光方盒、跑酷追击和 TNT飞跃使用各地图的 `schematics/<地图名>/arena.schem` 生成复制场地；匹配赛建保留管理员手建的资源大厅，只选择其边界，并使用 `schematics/base.schem` 生成队伍基地。这五类游戏允许多张地图绑定到同一个物理世界，各地图通过各自的选区、锚点和直线复制布局占用互不重叠的区域；TNTRun 与匹配赛建赛后只恢复本地图的 schematic 区域，不会重载共享世界。匹配赛建 0 号基地只作模板，实际队伍从 1 号基地开始分配；大厅与基地各设置一个传送门落点即可双向路由。复制数量、布局和所有锚点都由各自的向导步骤配置。

激光方盒通过 `/cc map edit laserbox` 编辑：用 WorldEdit 选取完整的 0 号场地，点击“保存场地模板”，再点击“批量生成比赛分区”输入场地总数（包含 0 号场地）。生成保留原建筑，沿 X 轴按模板宽度加 128 格隔离空隙、向上对齐到区块的间距复制；重新生成会先清除原布局的旧副本。双方出生点、观战点、补给点和边界只设置 0 号场地，副本自动平移这些坐标。完成后校验并发布；正式比赛同轮需要至少 `队伍数 / 2` 个场地。

TNT飞跃保存0号赛道模板时会同时记录选区边界，无需另选游戏边界。模板选区决定副本粘贴原点、水平范围和顶部；“设置淘汰高度”单独输入绝对 Y 坐标（`elimination-y`，支持负数和小数），玩家低于该高度时出局，即使此时已在模板底部以下。

跑酷追击的每个复制场地是一整个双赛道对局单元：对局位 A、B 各有一个准备点；赛道 1 同时承载 A 队追击者与 B 队逃跑者，赛道 2 同时承载 B 队追击者与 A 队逃跑者。每条赛道分别配置一个完整活动边界、一个追击者出生点和一组逃跑者出生点，不存在彼此独立的“追击区”和“逃跑区”。

每张地图都可配置赛前规则介绍。设置 `introduction-spawn-point` 和 `rules` 后，玩家会先进入规则介绍阶段；将介绍点留空或把 `rules` 设为 `[]` 即可跳过。

### 匹配赛建蓝图

执行 `/cc map edit buildmart` 并选择地图，在步骤菜单选择“小建筑修改与新建”。点击已有小建筑后，插件会将其放入队伍基地场地 0 的第一个普通建筑区并传送玩家过去；“新建小建筑”先输入名称，再进入空建筑区。修改保留名称和星级，新建时自动评星。

完成后右键该建筑区的实体提交按钮，也可使用菜单的提交按钮或工具栏保存按钮。提交时检查当前地图已保存的材料区快照：无法直接提供或通过支持的合成、烧炼、切石获得的材料会拒绝提交，并保留现场供继续修改。六个方向都被相邻完整不透明面遮挡的方块仅提醒，地面按场地 0 的实际材质检查；楼梯、台阶只按紧邻面的形状判断，玻璃不算遮挡。成功提交后更新蓝图库、恢复临时建筑区并传送至主大厅传送门出生点；取消、退出编辑或掉线时也会恢复建筑区。

用 WorldEdit 选择成品建筑后执行：

```text
/cc map blueprint create <蓝图名> [覆盖星级]
/cc map blueprint audit <蓝图名|all> [地图] [页码]
/cc map blueprint preview <蓝图名|all> [地图] [页码]
```

插件会忽略空气，把方块保存为相对选区最小角的偏移并立即重载蓝图库。蓝图长、宽、高均不能超过 7 格，文件位于 `buildmart/blueprints/<名称>.yml`；目录为空时会写出三个示例蓝图。

蓝图不应包含只用于展示的整片地形底板；船底、篮底、表盘、站台、舞池、主体台基及植物必需的局部基质属于建筑结构，应保留。2026-09-20 对现有 135 张蓝图逐张检查，调整了 27 张并重新评估受影响星级，详见 [Build Mart 检查记录](tools/buildmart-review-2026-09-20.md)。对应精确迁移为 `python3 tools/buildmart_floor_migration.py <blueprints目录> --apply`，仅处理清单中经过检查的旧版本，遇到其他改动会拒绝覆盖。

完成判定以蓝图文件为准，展示与玩家建筑均从所选地板最小角上方一格开始。草方块与泥土、菌岩与下界岩不再因上方遮挡而互相替代；额外方块仍按现有规则忽略。活板门、栅栏、栅栏门、生长年龄与铜蜡层的原有匹配规则保留。树叶忽略原版自动计算的叶距，种类、持久性和含水状态仍须一致。普通提交失败会显示缺失、材质错误、状态错误三项数量。加载时坏行、重复坐标、越界、空蓝图会整张拒绝并记录文件名和列表项编号；导出时拒绝现场缺少支撑的方块。

各队三个普通建筑区的提交按钮正上方三格会显示当前蓝图的全部材料，每行两种，格式为“橡木 × 4  涂蜡的切制铜台阶 × 1”；材料名称采用客户端原版译名。数量按实际放置材料统计，双层台阶计两块，门、床和双格植物按一件计，墙面告示牌/旗帜使用对应物品名，盆栽列出花盆与植物；订单完成时移除，下一张订单出现时更新，黄金建筑区不显示。玩家携带的资源地图绑定当前场地世界，每位玩家只看到自己的位置和朝向，超出地图范围时在边缘显示自己的标记。

黄金轮换共用比赛倒计时，比赛终点保留当前建筑结算部分得分；黄金两次确认只接收主手，并绑定玩家、队伍、槽位和本轮订单。普通及共享黄金展示区按完整 7×7×7 空间和底部地面保护交互与物理变化，流体和活塞不能跨越独立建筑区/材料区边界；门、床等多方块放置逐格校验。

建材区各自独立补货：成功采集后开始计时，每次再次采集都会重置计时，连续 20 秒无人采集后恢复该区域的方块快照。未被采集的区域不会定时刷新；比赛开始和地图重置时仍会恢复全部建材区。

匹配赛建中的铜不会自然氧化，蓝图匹配和材料审查不区分涂蜡状态。保存蓝图时会去除全部铜蜡层；凡是不能由同氧化阶段完整铜块即时合成或切石获得的部件（铜栏杆、铜链、铜箱、铜门、铜傀儡雕像、铜灯笼、铜活板门、避雷针），都会统一成未氧化版本。保存材料区时也会把涂蜡铜快照规范化为同氧化阶段的普通铜。

保存匹配赛建材料区时，插件会扫描当前选区并生成 `buildmart/material-manifests/<地图>.yml`。该文件按材料区和总计记录非空气方块的 `minecraft:<material>` 数量，同时保留精确 `BlockData` 数量，供检查全部建筑的材料需求是否被资源大厅覆盖，也是编辑器提交小建筑的材料审查依据。清单缺失或快照已变化时会拒绝提交，需重新保存材料区。

可使用 `scripts/buildmart_blueprint_audit.py` 检查单张蓝图或整个蓝图目录。脚本会结合方块数、材料种类、材料岛数量、高度、离散结构、方向和其他 `BlockData` 复杂度生成难度分数，并依据材料清单报告直接覆盖、可合成覆盖和未覆盖材料。例如：

```text
python3 scripts/buildmart_blueprint_audit.py <蓝图文件或目录> \
  --manifest <material-manifests/地图.yml> \
  --area-config <areas/地图.yml> \
  --markdown /tmp/buildmart-audit.md --csv /tmp/buildmart-audit.csv
```

## 比赛流程

### 手动测试赛

手动模式适合验图和单场测试：

1. 确保参与队伍的成员已经加入数据库并上线。
2. 确认目标场地处于 `WAITING`，没有其他比赛占用队伍或玩家。
3. 让观众执行 `/cc spectate <游戏> <场地> [实例]`，或直接打开 `/cc spectate` 菜单选择。
4. 使用对应 `/cc game start ...` 命令开赛。
5. 插件负责准备倒计时、传送、物品和效果初始化、计时、胜负判定与积分记录。
6. 单场或正式赛最终轮结束后玩家返回大厅并写入积分；正式多轮赛的中间轮留在场地安全点并直接进入下一轮。需要模板复原的地图会在整场结束后重新加载。
7. 用 `/cc rank playerboard`、`/cc rank teamboard` 检查结果。

同一支队伍或玩家不能同时进入多个场地。如果开始命令没有生效，应优先检查场地状态、队伍名称、队伍是否已在其他游戏中，以及地图必需点位是否完整。

### 正式赛事建议流程

1. 准备一份比赛就绪的赛事配置，包含固定羊毛色队伍、注册玩家和项目列表，并获取 Core 导入链接。
2. 执行 `/cc event teams import <赛事配置链接> --confirm`，原子结束上一届积分并整体替换正式队伍。
3. `/cc admin vote start` 开放下一项目投票；玩家使用 `/cc vote` 投票，随后 `/cc admin vote end` 公布结果。
4. 管理员执行 `/cc event start <游戏>` 启动正式赛程；未导入赛事时直接使用服务器现有队伍，已导入赛事时只能启动该赛事游戏列表中的项目，已归档赛事需先导入下一届。Tab 补全会列出全部已启用且支持赛事的游戏，无需先导入赛事。`riptide`、`frostbite` 和 `laserbox` 均支持此入口；`sulfursoccer` 等决赛游戏沿用总榜前二的决赛流程，也可使用 `/cc finale <游戏> start <场地>` 指定场地。
5. 调度器广播项目介绍和积分规则，进行 10 秒倒计时；游戏结束事件触发下一小轮，小轮之间默认等待 30 秒。
6. 全部小轮结束后，调度器广播本项目积分和总榜，并将观众移出场地。
7. 全部项目结算且无正式赛程运行后，执行 `/cc event export [冠军队伍]`。JSON 写入 `plugins/ChampionshipsCore/exports/<赛事标识>-results.json`，包含赛事 ID、固定游戏键、版本、玩家 UUID 和已加权积分，在 cc-web 上传发布。未填写冠军时，上传前必须在网页选择最终冠军，不能把积分第一自动当作冠军。

## 正式赛事命令

| 命令 | 行为 |
| --- | --- |
| `/cc event teams import <赛事配置链接> --confirm` | 校验并导入比赛就绪的赛事、固定羊毛色队伍和注册玩家；旧有效积分失效、旧轮次和队伍在同一数据库事务内清除 |
| `/cc event start <游戏>` | 所有已启用游戏均可无需导入，使用现有队伍启动正式赛程或默认场地的冠军决赛；同一项目运行中再次执行会紧急停止 |
| `/cc event export [冠军队伍]` | 导出当前赛事的团队/个人积分、UUID 与游戏版本；可指定最终冠军。文件位于 `plugins/ChampionshipsCore/exports/<赛事标识>-results.json` |
| `/cc finale dragoneggcarnival start <场地> [队伍1 队伍2]` | 在指定场地启动龙蛋狂欢决赛；未指定队伍时按总榜选择前二 |
| `/cc finale dodgebolt start <场地> [队伍1 队伍2] [--force]` | 在指定场地启动躲避箭决赛；未指定队伍时按总榜选择前二，`--force` 允许使用在线子阵容 |
| `/cc finale sulfursoccer start <场地> [队伍1 队伍2]` | 启动硫方足球决赛；未指定队伍时按总榜选择前二 |
| `/cc finale <游戏> cancel` | 取消决赛准备，或强制结束正在进行的正式决赛 |
| `/cc event stop <游戏>` | 显式停止该项目的赛程任务和运行实例 |
| `/cc event reset --confirm` | 重置正式比赛轮次和游戏顺序 |
| `/cc event undo --confirm` | 停止并撤销最近一轮正式比赛及其成绩 |

正式赛程支持全部已启用游戏。斗战方框、跑酷追击和激光方盒需要偶数支队伍和足够的场地副本；激光方盒同轮需要 `队伍数 / 2` 个空闲副本，最多九轮。三种 1v1 匹配项目的前半程使用随机后的循环赛抽签，轮数为总轮数向上取整的一半；从下一轮开始，每轮结束后按截至上一轮的累计胜负（胜 1 分、平 0.5 分）重新生成强强、弱弱配对，并通过历史对手记录避免重复交手。去到另一边会依次使用已加载地图；其他游戏按各自赛程管理器选择地图和轮数。

### 硫方足球决赛（sulfursoccer）

场地通过 `sulfursoccer/<场地>.yml` 与已发布的世界快照加载。两侧混凝土装饰的换色位置由 `right-team-color-blocks` 和 `left-team-color-blocks` 配置，使用整数 `x:y:z` 坐标；比赛准备时按双方参赛队伍颜色换色。

使用 `/cc map edit sulfursoccer` 新建球场，设置整个球场、互不重叠的两侧半场、两侧球门内部空间、中圈足球出生点、球场外观战点，以及每队恰好四个不同的出生参考点（依次为中场三点及球门前的独立白色标记点），再校验并发布。开赛时中场三点按参考点横向范围均匀分布，第四人出生在己方球门前、球门外的独立白色标记上；门前标记支持石英或白色混凝土，必须独立于白色线条，且上方两格为空；找不到时会提示并中止启动。有多块候选标记时，必须在编辑器中把第四点设在目标标记上。球门选区只包含门框内的空气和球门深度；球体中心进入选区即可得分。半场只约束出生点，开赛后可以跨过中线争球。

足球使用吸收白桦木板的成年硫方怪，保留原版击打、推动和弹跳物理。双方各支持 1–4 名在线队员，禁止攻击玩家、破坏球场、拾取物品或用桶和剪刀改变足球。正式决赛在规则介绍后进行 3 分钟试踢，动作栏和侧栏显示剩余时间；试踢进球不计分，球进门、出界或失效时只重置足球，不中断试踢。试踢结束后清除场内珍珠、恢复双方出生位置及珍珠冷却，从 0:0 开始正式比赛。仅首次正式开球显示“硫方足球即将开始”及倒计时，结束后显示“开球”；之后进球或出界重开只显示数字倒计时，结束后仅显示“开始”。将足球送入对方球门得一球，乌龙球也计入对方比分。进球后双方回到各自出生点，足球回中圈，倒计时后开球；出界或球体失效只重新开球、不计分。选手掉线时自动暂停（试踢计时也暂停），全部选手重连后继续。

试踢与正式比赛均给每人一颗可重复使用的末影珍珠，放在快捷栏第九格；试踢开始及首次正式开球时立即进入完整的 8 秒冷却，每人两次投掷间至少间隔 8 秒，进球重开不会清除冷却。投掷后自动补回珍珠，落地无伤害；落点必须在球场边界内，且玩家脚部不得高于球场地面 2 格，否则取消传送。暂停、介绍及开球倒计时期间不能使用珍珠，重开和结束会移除尚在飞行的珍珠。

`sulfursoccer/<场地>.yml` 的 `goals-to-win` 默认 5，`kickoff-countdown` 默认 5 秒。正式比赛从首次开球起限时 12 分钟，进球及出界后的重开倒计时计入限时，赛前试踢与掉线暂停不计入。比分及剩余时间显示在侧栏和动作栏；先达到目标球数或限时结束时领先的队伍获胜。12 分钟结束时仍平局则进入点球大战，正式比分保留，点球比分单独记录，不写入总榜积分。

点球双方交替射门，每队先射满 4 球，四人队伍按比赛出生顺序让每人射门和守门各一次；人数不足四人时循环轮换，仍各射 4 球。若此后仍平局，继续按原顺序双方各射一球，只在双方完成同一轮后比较比分，直到决胜。每球先准备 3 秒，射手随后在 15 秒内空手攻击足球一次，击球后最多等待 8 秒判定；击中玻璃板、出界、失效或超时均记为未进。射手可在隔离线后横向调整，不能靠近、接触推动足球或再次击球。守门员固定在球门内，不可击球，快捷栏前三格分别为“挡左”“挡中”“挡右”，切换物品或点击对应物品即可选择玻璃板挡住的三分之一球门；左右以守门员面向射手时的视角为准。其他球员在观战点等待，点球期间禁用珍珠，掉线时暂停当前射门和计时。

点球位置根据球门选区自动生成，支持沿 X 或 Z 轴的球场。球门须至少宽 3 格、地面上方高 2 格，门前须留出至少 8 格球场空间，球门口外一格的挡板位置必须为空气；不满足时校验或启动会提示。每次换方向、换球、结束或取消比赛时恢复原方块。使用 `/cc finale sulfursoccer start-direct <场地> <队伍1> <队伍2>` 可跳过正式决赛的总榜选队、规则介绍、三分钟试踢和自动观战调度；`/cc finale sulfursoccer cancel` 可取消正式决赛。

主配置需启用 `SulfurSoccer`，`formal-events.SulfurSoccer.maps` 可指定默认球场。此版本主配置为 25、消息配置为 62；配置版本必须与当前模板一致，更新配置时请使用当前模板重新填写自定义值。

## 投票、积分与观战

投票持续 120 秒，只允许已加入队伍的选手投票。已经记录为完成的游戏不能再次被投票；结束时插件按票数广播排行。

每个场地在比赛中累计玩家积分，结束时写入数据库。`weighted-score.enabled` 开启后，总榜会应用游戏归一化权重；存在已导入的活动赛事时，再叠加该赛事的单游戏积分权重和轮次倍率。没有活动赛事时，轮次倍率回退到 `weighted-score.round-multipliers`。`/cc rank info` 可查看动态归一化权重。

在正式赛事模式中开启 `strict-spectator-rule` 后，正常赛事轮次中的参赛队员不能随意观战；拥有 `cc.refuge` 的裁判或替补不受此限制。DAILY 模式始终跳过该判定。

## 聊天与跨服展示

Core 与 Worker 的比赛聊天使用 `玩家名 <队名> » 消息` 格式，日常聊天保留 `[标签] 玩家名 » 消息` 格式；加入/退出消息和 TAB 使用 `[标签] 玩家名` 格式。队伍颜色、活动选手状态和聊天模式由共享的 `PlayerPresentation` 提供，跨服聊天也保留发送方的模式。拥有 `cc.admin` 或 `cc.refuge` 的玩家可在公共聊天中使用 `&c` 颜色、`&l` 加粗、`&n` 下划线等格式代码，也支持十六进制颜色，跨服转发会保留这些格式。Worker 会从 manifest 投影本局原生队伍，并在平台不支持队伍变更时降级为插件侧 `/teammsg`、`/tm` 处理。

启用 Redis 后，Core 和 Bingo Worker 的普通聊天会写入同一命名空间的聊天流，再由每个实例各自的 consumer group 投递给本服玩家和控制台。聊天依赖稳定且唯一的 Core `redis.instance-id` 与 Worker `worker-id`；重复 ID 会共享消费进度并造成实例漏收。Redis 不可用时，本服聊天由 Paper/Folia 正常显示，跨服转发暂停。`/teammsg` 始终只面向当前比赛队伍。
