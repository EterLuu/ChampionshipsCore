# 旁观、实体显隐与 Tab 契约

本契约适用于 ChampionshipsCore 全部游戏、正式赛与日常局、Core 本地 Bingo 和独立 Bingo Worker。新增游戏以及修改监听器、定时任务、GUI、管理命令、占位符、发包或生命周期时，都必须检查这些规则。逐游戏审查方法见 [显隐验证指南](../tools/spectator-visibility-audit-2026-10-03.md)；本文件定义后续开发必须保持的行为。

## 玩家可见性

实体可见性与 Tab 列表是两个独立的输出，不能用同一项隐藏操作同时决定二者。

| 查看者 | 游戏玩家实体 | 旁观玩家实体 | Tab 列表 |
| --- | --- | --- | --- |
| 旁观玩家，包括已转入旁观的参赛者 | 允许查看全部玩家，覆盖游戏的队友、距离、冲刺、会话隔离和隐身限制 | 允许查看其他旁观者 | 保留全部在线玩家及正常展示字段 |
| 正常游戏玩家 | 使用该游戏已有的队友和其他显隐设置 | 不允许查看，包括原参赛者转成的旁观者 | 保留全部在线玩家及正常展示字段 |

“允许查看全部”指显隐策略不得排除目标，不要求跨世界或超过 Minecraft 原生实体追踪距离强行渲染实体。旁观者不得使用“只显示某人/某队”的隐藏筛选；传送对象选择不改变实体可见性。

Parkour Warrior 的队友显示、Ace Race 的开场隐藏/距离可见/冲刺隐藏，以及 Riptide Rush（命令 `riptide`）等游戏的既有规则继续用于正常游戏玩家。不能为了修复旁观而把正常玩家统一设为 ALL，也不能把这些机制直接应用到旁观者。游戏的隐身药水和按查看者处理的描边/隐身同样需要区分查看者身份。

Tab 必须对所有查看者保留全部在线玩家。禁止删除或取消列出仍在线的真实玩家，禁止按队伍、旁观身份、比赛分区、会话或实体隐藏策略筛选 Tab。头像、名称、队伍/比分展示、延迟、排序、签名聊天资料等字段必须保持其正常含义。真实离线玩家必须及时移除，重连不得留下旧条目或缺失新条目。

## 真实模式与客户端呈现

任何旁观玩家的服务器模式必须是 `GameMode.SPECTATOR`。禁止把 Adventure + 飞行/无碰撞/无敌/隐身药水当作替代旁观实现。服务器模式是行为依据，客户端收到的 Adventure 值只是呈现。

共享发包层必须把 Spectator 呈现为 Adventure，覆盖自己的模式变化、所有接收者的玩家信息，以及登录、重连、复活和跨维度的登录/重生包。当前相关包包括 `PLAYER_INFO_UPDATE`、`CHANGE_GAME_STATE`、`JOIN_GAME` 和 `RESPAWN`；协议升级时必须复核是否存在其他承载模式的路径，不能仅修改 Tab 的模式字段。

旁观者以 Adventure 客户端呈现时仍必须看得到隐身玩家的实体。玩家元数据投影仅移除该视角不应生效的隐身标记，必须保留其他标志和正常玩家的游戏隐身规则；退出旁观后重新同步真实元数据。中途加载时须修正已经缓存的本机模式与实体元数据，不能只等待下一次模式事件。

旁观状态使用统一的飞行、无碰撞、无物理碰撞、免伤、不可拾取、不影响生物生成和睡眠统计等保护。旁观者不得骑乘或附身其他实体，摄像机保持自身。有限效果的恢复不得重新获得进入旁观前的完整时长。

## 职责与接入限制

| 组件 | 职责 |
| --- | --- |
| Core `SpectatorManager` | 旁观身份查询、原始状态、控制物品、状态恢复、传送请求与生命周期 |
| Core `PlayerVisibilityManager` | 接受游戏显隐策略，计算并应用玩家实体显隐，释放自身隐藏关系 |
| Worker 比赛 roster / `WorkerMatchRegistry` | 比赛归属与角色，以及真实模式对应的旁观判断 |
| Worker `WorkerVisibilityManager` | Worker 玩家实体显隐与释放 |
| 平台 `SpectatorStateService` | 两端共用的无状态旁观标志操作 |
| 平台 `PlayerPacketPresentation` | 两端共用的模式/元数据投影和完整 Tab 列表，不决定服务器角色或游戏实体策略 |

游戏决定谁在死亡、完成、失败、退出重进或新回合时转入旁观、何时恢复游戏。死亡/完成/淘汰名单和参赛 roster 继续用于游戏结算与恢复，不得把它们另做一套独立的旁观保护或隐身系统。外部观众与转入旁观的参赛者必须获得相同的基础状态与行为保护；游戏卡片、描边等只读展示可由场地覆盖层补充。

所有身份判断都必须使用统一入口，不能以无队伍、某件控制物品、客户端 Adventure、缓存的 Player 对象或某个游戏名单单独判定旁观。命令、GUI、占位符、移动路由和定时任务同样遵守这一限制。

Core 游戏机制通过已绑定运行实例的 `BaseListener` / `SpectatorGameEventGate` 接入，共用移动路由处理旁观身份。新增事件必须检查事件玩家、实体、攻击者、目标及投射物来源。加入、退出、复活等恢复事件必须能到达其所有者，不能通过一律取消事件破坏生命周期。

事件拦截不能替代资格检查。直接调用入口和周期任务必须重新检查 `isGameplayParticipant` 或对应 Worker 资格，旁观者不能提交建筑、到达检查点/终点、触发跳板、采集补货、完成 Bingo 目标、参与数学/踩色/节奏/碰撞判定、承受游戏扣血或触发延迟攻击等玩法。只读 UI、正常状态展示和必要的释放/恢复工作可以继续。只有游戏恢复正常状态后才重新开放玩法。

禁止在游戏 Handler、Area、GUI、Command 或其他辅助类里另存一套 hidden-player/旁观保护状态，或直接对玩家调用 `hidePlayer`、`showPlayer`、`hideEntity`、`showEntity` 实施旁路显隐。游戏应向统一管理器提交 UUID 策略；文本展示实体等游戏资产的显隐与玩家实体显隐须明确区分。允许的共享 helper 和网络缓存只能承担上述既定职责，不能成为第二个角色所有者。

## 生命周期与线程要求

| 场景 | 必须保证的结果 |
| --- | --- |
| 加入、重连 | 以当前连接和游戏归属恢复角色；双向重算显隐；Tab 完整；游戏明确决定正常或旁观，即使设置同一模式本来不会产生事件 |
| 开始、规则介绍、倒计时、新回合 | 尊重游戏对模式的决定；真正处于旁观的参赛者仍受统一保护，恢复正常后解除保护并恢复游戏策略 |
| 死亡、复活 | 正常玩家交由游戏决定；旁观者不参与死亡计分或玩法；实际复活后重新应用有效身份、元数据、Tab 与显隐 |
| 正常结束、失败、中止、重置、dispose | 释放当前所有者的任务、会话、控制物品与隐藏关系；失效回调不得重建旁观或改动新一局状态 |
| 退出、转服 | 取消待传送请求，持久化安全状态；保留或释放 UUID 归属由游戏决定，不能长期持有旧连接 |
| 配置热重载 | 使用既有 `GameManager.hotReload` 和回滚/中止规则，不重复注册监听器或循环任务，不通过整套 unload/load 偷换热重载语义 |
| 插件卸载、重新加载、中途加载 | 卸载后排队的回调不能再次隐藏或改变角色；中途加载必须接管已有在线 Spectator 和已知旁观归属 |

旁观传送先异步预热目标区块，实际传送前在正确线程核对当前玩家连接、会话、场地、插件状态及最新请求。后续选择、离开、断线、场地释放或重载必须使旧请求失效；仅在 `teleportAsync` 已完成后检查归属不足以防止旧传送。旧场地的清理不得夺走新场地的状态。

持久身份和所有权使用 UUID；在线 Player/Entity 仅在当前连接和正确线程上操作。Paper 使用服务器线程，Folia 的玩家操作及原生信息捕获/发送使用对应实体线程。捕获传送目标位置也必须遵守目标实体的线程所有权；处理调度拒绝、retired、失败和关闭路径，不允许阻塞游戏线程等待 Future。

多人同时切换模式时合并并针对查看者补发元数据，避免每个模式事件都再次全服互相广播形成立方级工作量。关闭管理器必须取消循环任务、注销监听器并阻止已排队工作继续生效。

## 修改与验证门槛

1. 根据 `GameTypeEnum` 当前清单逐一检查全部游戏，不能只检查命名示例或 Git Diff。覆盖 Handler、直接入口、循环/延迟任务、GUI、命令、占位符、加入/退出、结束/中止及恢复调用方。
2. 共享变更同时检查 Core 与 Worker 的实现、默认资源、运行配置和测试。运行配置只做对应键的增量修改，保留颜色、占位符、坐标及其他自定义值；已兼容的另一侧必须说明依据。
3. 测试至少覆盖旁观互见、旁观参赛者、队友/SELF/显式策略、跨会话、真实隐身、完整 Tab 与真实离线移除；覆盖自己与他人的模式包、进入/退出旁观后的元数据，以及上述生命周期和旧回调失效场景。
4. 涉及发包、原生反射或 Folia 调度时，在受支持 Paper/Folia 版本上做相应原生验证；编译或纯策略测试不能单独证明实际网络呈现和线程正确性。保留四连接等验证场景的模式、Tab、实体标记、退出/重连和清理后证据，区分代码审查、隔离验证与生产验收。
5. JUnit 和测试工具位于各 Maven 模块的 `src/test/java`，保持同包名；临时原生探针与构建日志放系统临时目录。从根仓库执行 `mvn -B -ntp -pl championships-core,championships-bingo-worker -am package`，缓存完整时可使用 `-o`。
6. 成功打包后直接替换对应运行 JAR，不创建 JAR 备份，不例行做额外归档完整性校验。双方代码发生变化时部署双方，并明确 Core 与 Bingo Worker 都需要重启；仅改本文等文档不需要重新打包或部署。

当前实现依赖已安装的 PacketEvents，并使用受支持的 Paper 26.2 原生玩家信息包保留头像和签名会话。升级服务端、PacketEvents、玩家信息协议或原生字段/方法时，必须重新验证契约，不能用会破坏 Tab 或真实旁观语义的静默降级绕过失败。
